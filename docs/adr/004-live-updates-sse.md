# ADR-004: Live-обновления по SSE с досылкой пропущенных патчей

## Статус

Принято (этап 3).

## Контекст

Требования: сервер поддерживает обновления в реальном времени; клиент реализует
WebSocket, SSE или эффективный поллинг; патч применяется без полного рефетча;
индикатор соединения в шапке; экспоненциальный backoff при обрыве; кэш инвалидируется
только при реальном изменении данных.

Дополнительный риск, который хотелось закрыть: после обрыва соединения клиент
не должен ни молча расходиться с сервером, ни делать полный рефетч «на всякий
случай» при каждом реконнекте.

## Решение

### Транспорт — Server-Sent Events

`GET /api/org-tree/events` — поток событий `hello`, `patch`, `resync`, `ping`
(контракт в [data-model.md](../data-model.md#live-патчи)). Данные идут только от
сервера к клиенту, обратный канал не нужен — это ровно случай SSE: обычный HTTP,
проходит через тот же Vite-прокси, что и REST, отлаживается `curl -N`.

### Нумерация событий и досылка

Каждый патч имеет `seq` (= версия стора после применения) и передаётся как `id`
события. Сервер хранит кольцевой буфер последних 200 патчей. При переподключении
клиент передаёт последний полученный `seq` (`?lastEventId=`, аналог заголовка
`Last-Event-ID`), и сервер:

- досылает всё, что клиент пропустил (`hello { replay: true }` + патчи) — клиент
  догоняет без рефетча;
- если история уже вытеснена или сервер перезапущен (версия «из будущего»), шлёт
  `resync` — клиент делает один полный рефетч.

Дополнительно `hello` несёт `etag` текущего снимка. Если досылки нет и ETag
клиента отличается — данные изменились между `GET` и подключением потока, клиент
инвалидирует кэш. Так полный рефетч случается только при реальном расхождении.

### Переподключение управляется клиентом

Нативный `EventSource` переподключается сам, но с фиксированной паузой и без
индикации. Поэтому `liveClient` при любой ошибке закрывает соединение и открывает
новое по экспоненциальному backoff: `min(30 с, 1 с · 2^n) + jitter(0..500 мс)`.
Джиттер защищает сервер от синхронного «шторма» переподключений.

Сторожевой таймер: если 45 с нет ни события, ни `ping` (heartbeat каждые 15 с),
соединение считается зависшим и переподключается. Heartbeat — именно событие,
а не SSE-комментарий: комментарии `EventSource` клиенту не отдаёт.

`navigator.onLine === false` → статус «Нет сети», попытки не тратятся; по событию
`online` — немедленное подключение.

### Применение патча

`useOrgTreeLive` пишет патч прямо в кэш react-query через `setQueryData`:
новый массив узлов, в котором заменён только изменённый объект. Модель дерева и
агрегаты обновляются инкрементально (см. [ADR-005](005-incremental-aggregation.md)).
Контроль непрерывности: если `seq` пришёл не следующим по порядку — рефетч.

## Альтернативы

- **WebSocket.** Двунаправленный канал здесь не нужен; пришлось бы самому писать
  heartbeat/ping-pong, реконнект и нумерацию, а через dev-прокси WS требует отдельной
  настройки. Преимуществ для одностороннего потока патчей нет.
- **Поллинг с backoff.** Даже «умный» поллинг делает пустые запросы при отсутствии
  изменений и даёт задержку до интервала опроса. SSE даёт push без пустых запросов,
  а ETag/304 уже покрывает случай, когда поток недоступен.
- **Полный рефетч при каждом реконнекте.** Проще, но противоречит требованию
  инвалидировать кэш только при реальном изменении и плохо масштабируется.

## Последствия

- В dev-режиме Vite-прокси не транслирует обрыв бэкенда в открытый SSE-ответ:
  в `vite.config.ts` добавлены обработчики `error`/`proxyRes close`, которые
  завершают ответ клиенту. Без этого индикатор узнавал бы об обрыве только по
  сторожевому таймеру.
- Сервер хранит буфер патчей в памяти; при перезапуске версия начинается с 0 и
  клиенты получают `resync`.
- SSE ограничен ~6 соединениями на домен в HTTP/1.1 — для дашборда с одной вкладкой
  несущественно, для прода решается HTTP/2.
