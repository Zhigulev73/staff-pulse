Правило зависимостей: `app → features → shared`; `shared/model` не знает о React,
`shared/api` не знает о модели. Абсолютные импорты через `@/`.

## Поток данных: от API до UI

1. `App` вызывает `useOrgTree()`. TanStack Query смотрит в кэш по ключу `['org-tree']`.
   Если данные свежее 5 секунд — запроса нет, компонент сразу получает их.
2. Иначе выполняется `queryFn`: берёт ETag предыдущего ответа из кэша и вызывает
   `fetchOrgTree({ etag, signal })`. `signal` — AbortSignal от react-query: при
   размонтировании последнего подписчика запрос отменяется.
3. Сервер сравнивает `If-None-Match` со своей версией. Совпало — `304` и клиент
   возвращает **прежний объект кэша**: ссылки не меняются, ничего не перерендеривается.
   Не совпало — JSON, который проходит `parseOrgTree` (zod). Любое отклонение от
   контракта превращается в `InvalidResponseError` и состояние `isError`.
4. `App` получает `{ nodes, etag }` и вызывает `getOrgModel(nodes)`. Модель (дерево,
   уровни, агрегаты) строится один раз и мемоизируется по ссылке на массив узлов —
   переключение вида, выбор строки, раскрытие веток её не пересчитывают.
5. Состояния: `isPending` → `LoadingState`; `isError` → `ErrorState` с кнопкой
   «Повторить» (`refetch`); пустой массив → `EmptyState`; иначе панели дерева и таблицы.
6. Раскрытые узлы хранит `useExpansion`: по умолчанию раскрыты корни (дивизионы),
   поэтому второй уровень виден сразу. Выбор пользователя хранится отдельно и не
   сбрасывается при рефетче.
7. `rowsFromModel(model)` даёт строки таблицы (мемо по ссылке на модель). `OrgTable`
   применяет к ним фильтр (значение поля через дебаунс 250 мс) и сортировку —
   чистые функции `filterRows`/`sortRows` внутри `useMemo`.

## Общее состояние дерева и таблицы

`App` — единственный владелец состояния, которое должно быть согласовано:

- `selectedId` — узел, выбранный в дереве или в таблице; оба компонента controlled.
  Выбор из таблицы дополнительно вызывает `reveal(id)` (раскрыть предков), а дерево
  прокручивает строку в видимую область.
- `expandedIds` — раскрытые ветки (`useExpansion`).
- `view` — «Дерево / Таблица» для экранов уже 1280px; от 1280px обе панели видны и
  переключатель скрыт CSS-медиазапросом.

Фильтр и сортировка — локальное состояние `OrgTable`: они не влияют на дерево и на
агрегаты, поэтому в общее состояние не поднимаются.

## Поток live-обновлений

```
simulator ──applyChange──▶ store ──subscribe──▶ sse.ts ══ event: patch ══▶ liveClient
                            │ version++, буфер                                 │ zod, seq
                            ▼                                                  ▼
                     GET /api/org-tree                                  useOrgTreeLive
                     ETag "v<version>"                                         │
                                                        setQueryData(['org-tree'], applyPatch)
                                                                               │
                                              ┌────────────────────────────────┴──────────────┐
                                              ▼                                               ▼
                                   новый массив nodes                              highlightStore.flash(keys)
                                   (заменён 1 объект)                                         │
                                              │                                               ▼
                                   patchModel → registerModel                    FlashCell ячеек узла и предков
                                              │                                        (CSS-анимация 1.5 с)
                                              ▼
                                   getOrgModel(nodes) — мгновенно
                                              │
                                              ▼
                                   OrgTree / OrgTable (перерисовка только затронутых строк)
```

1. `useOrgTreeLive` открывает SSE-поток при монтировании `App` и закрывает при
   размонтировании (`liveClient.stop()`).
2. `hello { version, etag, replay }` — если досылки не будет и `etag` отличается от
   кэша, кэш инвалидируется (данные изменились между `GET` и подключением).
3. `patch` валидируется схемой, проверяется непрерывность `seq`; затем `applyPatch`
   кладёт в кэш новый массив узлов и регистрирует инкрементальную модель.
4. Затронутые ячейки (изменённые поля узла + агрегаты узла и предков) получают
   подсветку через `highlightStore`; каждая `FlashCell` подписана на свой ключ.
5. Обрыв: `liveClient` закрывает соединение и переподключается по экспоненциальному
   backoff, статус идёт в `ConnectionIndicator`. При реконнекте передаётся
   `lastEventId`; сервер досылает пропущенное или присылает `resync` → один рефетч.

## Кэширование и лишние запросы

- `staleTime: 5000` — окно, в котором повторные подписки на ключ не порождают запрос.
- `refetchOnWindowFocus` и `refetchOnReconnect` выключены: актуальность после первой
  загрузки поддерживает live-канал, а не «рефетч на всякий случай».
- Полный рефетч из live-канала происходит только по сигналу расхождения: `resync`,
  пропуск `seq`, несовпадение `etag` в `hello` без досылки.
- ETag/304: даже когда запрос всё же уходит (например, по кнопке «Повторить»), при
  неизменных данных сервер не шлёт тело, а кэш сохраняет прежний объект. Инвалидация
  происходит только при реальном изменении версии данных.
